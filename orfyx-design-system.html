01

The problem

Members want to walk into any gym with one pass. Owners want a zero-friction door — scan, validate, let them in. The system had to serve both sides with opposite needs: members browse in leisure light-mode contexts; owners operate one-thumb, at a busy front desk. And in-market reality: many members pay cash at the gym — so offline and pending states are first-class, not edge cases.

02

Principles

P1

Volt is a spotlight, not a fill

One electric accent — #E5FF3D — reserved for the single primary action and "live/active" signals. Everything else is ink and warm neutrals. If two things are volt, one of them is wrong.

P2

Failure paths are designed, not afterthoughts

Expired QR, declined payment, wrong venue, offline entry — every failure state got the same fidelity as the happy path, because the door is where trust is won or lost.

P3

Two apps, one language

Member and Owner share tokens, type and accent, but diverge in density and navigation: member is browsing-first and airy; owner is operational and compact.

P4

Cash is a first-class citizen

Pay-at-gym isn't a fallback — it's a designed loop: member requests → pass sits pending → owner validates cash/card in person → pass activates.

09

The QR pass — designed to fail well

The QR is the moment of truth, so it got the deepest treatment: a 5-minute rotating token, verified server-side (the client never self-validates), brightness-boosted on open, and cached to work offline. All four states shipped at full fidelity — on both sides of the door.

Active

Live countdown in volt; token auto-refreshes before expiry.

Expired

Token older than 5 min — one tap regenerates. No dead ends.

Used

Already scanned today — shows entry time so the desk can resolve disputes.

Invalid

Cancelled or bad signature — clear reason plus a support path.

The owner's scanner mirrors the same four outcomes — success (welcome), expired, wrong venue, invalid — so both people at the door always see the same truth.

System rules

Using volt without shouting

The accent survives across 80+ screens because its usage is governed, not vibes-based.

Do

One volt CTA per screen — the action that moves money or opens a door.

Do

Volt for live signals: occupancy dots, QR countdown, active pass state.

Don't

Volt backgrounds, volt text on cream, or two volt buttons in one view.

Don't

Use volt for errors or warnings — failure states get their own quiet reds and ambers.

12

Process

Storyboard first

The whole install → first-scan journey as numbered tiles, both payment branches included, before any hi-fi pixels.

Tokens before screens

Color, type, radius, elevation and density locked as CSS variables — every later screen consumed the contract.

Variations, then commitment

3 QR layouts, 3 bottom-nav styles, 4 social-button directions — explored side-by-side with live tweaks, one picked to ship.

Handoff by README

Each flow shipped with anatomy, tokens, states, state-to-wire and a suggested API surface — engineers rebuild against the contract, not screenshots.

13

What made it work

Tokens as the contract

Every surface consumes one CSS variable sheet. Radius, density and accent are tweakable presets — a rebrand-level change is a variable edit, and prototypes stayed pixel-consistent with handoff specs.

Designed failure = trust at the door

Expired / used / invalid QR, declined payments, offline entry and camera-permission-denied all shipped as designed states — the owner never improvises at the desk, the member never stares at a spinner.

Density instead of divergence

The owner app never forked the system — it flips a density token. Same components, tighter padding. Half the maintenance, twice the coherence.

Handoff-ready by construction

Every flow ships with a README spec: anatomy, tokens, states, API surface. Prototypes are references; engineers rebuild against the token contract, not screenshots.
